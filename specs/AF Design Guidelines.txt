3.6 3.1) Adaptive Form Types
This section describes the different Adaptive Form Types. Each type has different characteristics. For the

3.6.1 Single Adaptive Form
A Single Adaptive Form results from the "UBS" template. It can be used as a standalone form or be included
in a Form0 or Business Formset. The Single Adaptive Form has the following characteristics:
    •   Handles one main CDOK
    •   Only has one main document produced
    •   Can have consecutive attachments that are merged into the main document
    •   Can have individual attachments that result in separate PDF outputs (Annexes)


3.6.2 Form0
A Form0 is based on the Formset technology. It comes along with the overview page and includes Single
Adaptive Forms. The Form0 has the same characteristics as the Single Adaptive Form.
The Form0 approach can be used when:




                                                                                              3) Adaptive form – 33
                                                                                 UBS Forms – AF Design Guidelines




    • The Single Adaptive Form approach has technical limitations (Multiple titles, pages breaks, ...)
    • To achieve a better user experience with the overview page
The Form0 in the end is just another way of presenting a Single Adaptive Form. All "Main" documents of the
subforms will be merged together to achieve the single main document output since it handles the same
CDOK.


3.6.2.1 Example
An example for a Form0 is the adaptive form ABKA. It includes for Single Adaptive Forms as subforms. But
all of these subforms have the same CDOK in the metadata component (63126). Therefore, those subforms
can be merged together to one document and be processed as one by CLP/DPE.


3.6.3 Business Formset
A Business Formset is also based on the Formset technology. It also comes along with the overview page
and includes Single Adaptive Forms. The Business Formset has the following characteristics:
    • Handles multiple CDOKs
    • Produces one "Main" document per subform (CDOK)
    • Includes all individual attachments of its subforms
The Business Formset is what is considered a "real" Formset. Meaning it will also appear as such in Kiosk for
example (31.05.2021: Formsets are not yet displayed in Kiosk). Whereas the Single Adaptive Form and
Form0 will be presented as normal forms.


3.6.3.1 Example
An early example of a Business Formset is the adaptive form ACBU. This Business Formset includes the
following Single Adaptive Forms:

   1. Change of Name (61501)
   2. Change of Domicile (61502)
Since the CDOK is different between the subforms, multiple Main documents need to be created and
processed.

7.3.3 Additional information
Multilingualism
In case of the Custom XDP, each language has its own XDP template. Hence every adaptive form with a
Custom XDP has multiple XDP’s. To keep the level of configuration low, the business logic looks up the
proper XDP template according to the users locale (for example en_US). But in order for this business logic
to work, some rules need to be followed.
We assume that we have an adaptive form called “Change of address”. This adaptive form needs a Custom
XDP. Therefore, the following XDP templates were created:
     • ChangeOfAddress_en_us.xdp
     • ChangeOfAddress_en_gb.xdp




                                                                                           7) PDF generation – 97
                                                                                    UBS Forms – AF Design Guidelines




    • ChangeOfAddress_de_de.xdp
    • ChangeOfAddress_de_ch.xdp
1) Template file naming
The template files need to have the following structure and each section of the filename is explained below:
TEMPLATENAME_LOCALE.xdp


 Section                               Description / Rules


 TEMPLATENAME                          The TEMPLATENAME needs to be the same for all languages.
                                       Restrictions:
                                       The template name section cannot have an underscore (_) in it. The
                                       reason is that the logic assumes the locale (like en_US) after the first
                                       underscore in the template name.


 LOCALE                                The locale for which the template is designed. A locale can consist of
                                       two parts: The language and the variant. In case of en_US, “en” is the
                                       language and “US” the variant.
                                       In the locale part you can define the language and the variant (en_US)
                                       or just the language (en). This has an impact of the prioritization!
                                       Examples:
                                       ChangeOfAddress_en_us.xdp
                                       ChangeOfAddress_en.xdp
                                       Restrictions:
                                       Always use lower case in the LOCALE section.
                                       Use an underscore (_) to separate the language and the variant.


Prioritization
If the naming is properly done, the business logic looks for templates in the following prioritization:

   1. A template for the given language AND variant (for example en_US).
   2. A template for the given language (for example en).
   3. The template referenced in the configuration.



7.4 Custom XDP in a FormSet
A Form Set has the option to generate every subforms PDF individually (generation per subform). In this

11.5.1 Fire and Forget approach
Form submission cycle now creates logs under logs/ubsdata-clp.log. Upon adaptive form submission we
will capture the status specific to the form submitted in case:
    • The adaptive form submission is successful.
    • CLP integration fails.
The form submission is not blocked if CLP integration fails for any reason. With that approach, the user can
continue when the CLP integration fails. The DoR has the following differences when the CLP integration
fails:
    • No QR-Code with the UUID in it (visually)
    • The UUID in the custom property is empty
If the CLP integration is mandatory for a specific adaptive form and mandator, this can be configured in the
metadata component. In this case, the submit will fail when the integration with CLP is not successful.

The first parameter is needed to identify the adaptive form. This is important in case of a formset, where
multiple adaptive forms are handled at the same time. The second parameter can either be true (mandatory)

 Method                 GET

 Request            Form triple as part of the query params:
 information           • formcode: The 4 character formcode (ex. ABSD)
                       • mandator: The 3 digits for the mandator (ex. 001)
                       • language: The 2 characters for the language (ex. EN, DE, FR, IT, ES, ...)


 Response Type      The servlet returns a redirect status when the adaptive form was found and redirects
                    automatically to it.


 Validation         Triple validation
                    When one of the provided triple information is missing, the servlet returns an error.
                    Formcode validation
                    When multiple adaptive forms with the same formcode are found in the repository, the
                    servlet returns an error.
                    Language validation
                    The redirect service checks if the provided language is present for the given
                    formcode. When the given language is not present and it also doesn't match the
                    "Master Language", the servlet returns an error.
                    The service evaluates the relevant language. When 001 and DE is provided, a de-ch
                    translations needs to be present.

13.5.1 Translation not reflected for specific language


13.5.1.1 Root Cause
In the normal process, a form designer adds the languages in the author instance via "Add Dictionary". This
issue occurs when he misses out on a language and AEM doesn't create a dictionary entry for it. Lets
assume an adaptive form needs the following three translation:
    • DE-CH
    • FR-CH
    • IT-CH
The form designer forgets to add IT-CH in the process but requests it at ITT. ITT returns three language files
which the form designer is importing. Since IT-CH doesn't have a pregenerated dictionary entry, AEM creates
it on the fly. But this on-the-fly creation is not working properly. IT-CH will not work in that case.
The issue can be identified as follows:

   1. Open CRX and navigate to the form (/content/forms/af/...
   2. Display the language folder for the language that is not working. Example path:
      /content/forms/af/afforms_global_all/af_ac/AF_ACBH/jcr:content/guideContainer/assets/
      dictionary/de-ch
If the folder misses the attribute "sling:basename" and "jcr:primaryType" is "nt:folder" the translation does not
work. A proper translation folder looks as follows:

19.2.2 Saving a Draft
Upon clicking the "Save as draft" entry, the user is prompted with the draft dialog:




The "Draft Title" will be stored in MyOnlineForms along with the form data. The title is currently restricted to
50 characters. By clicking on "Save":

   1. The formData is stored in CLP and CLP generates a UUID. There is no PDF involved at this point.
   2. The retrieved UUID from CLP is used to store the draft in MyOnlineForms.
From that point on, the user can see the draft in MyOnlineForms right away. The user gets a notification in
the dialog box, whether the saving was successful or not.


19.2.3 Updating a Draft
When reopening a draft, the data is retrieved from CLP with the given UUID. The form is then prefilled with
that data. When the user reaches the Online Form, the data is already there. At any point in the Online Form
Journey, the user can "Save" the draft again. In case that there is already a UUID, no Draft Title Dialog is
prompted. The data is updated right away in CLP.
MyOnlineForms is also updated with the new timestamp and eventually with an updated CDOK.

19.2.4 Submit
When an Online Form is submitted, the following actions are executed:

   1. The generated PDF is stored under the draft UUID in CLP (with status "Final")
   2. The MyOnlineForms entry is also updated (with Status "Final")

23 23) AF Security

23.1 Background
In the first phase of the project, the Online Forms were not protected and only available to internal users. In
the future, Online Forms will be exposed to:
        GFIM Users
        E-Banking Users
        ...
Therefore, the security feature for Online Forms was introduced. In addition, internal users will also be known
via ISSO.



23.2 Technical Information

23.2.1 Users
In an out of the box setting of AEM Forms, the Publisher is not protected. When no authentication is
implemented, the user gets logged in as "Anonymous" user and has access to the Online Form. In order to
restrict the access, this user is restricted to access the forms CRX paths (/content/forms/af and /content/
dam/formsanddocuments).



         This configuration is part of the "afcomplib_all". When installed to an instance, this restriction
         takes immediate effect.


In addition to the restriction, two new users are introduced:


 User                                        Description

 ubs-internal-user                           Used when provided security context sent to MyOnlineForms
                                             indicates that the user is "Internal"


 ubs-external-user                           Used when provided security context sent to MyOnlineForms
                                             indicates that the user is "External"

        These users are also part of the "afcomplib_all" and are installed with the "apps" part. They
        currently have the same AEM Forms rights (to see an Online Form).

to MU9 (MyOnlineForms). The following graphic illustrates this and more information on the cases can be

29.1 Background
With the Refactoring of the "FormSubmitServiceImpl", the logging for the Submit was reworked. Note: This
change is currently implemented only in the submit. But the concepts and ideas can be taken into
consideration in other areas of the afcomplib_all. The idea is to have a comprehensible trace of logs
throughout the submit. These logs should also be linked to a specific submit.



29.2 Submit
This section documents the logging during a Online Form / renderDor Submit.


29.2.1 Concept
The main class for storing submit information is the class: FormSubmitContext. This class is instantiated at
the beginning of a submit. In contains the following information:



   FormSubmitContext Information


  {
      "submitTransactionId":"c42edc71-b994-44ed-b2f9-0b287b31021d",
      "browserlessDorRendering":false,
      "clpPersistenceAllowed":true,
      "userId":"43642842",
      "userType":"1",
      "draftUuid":"99e83180-79b8-418c-a130-664758753269",
      "xMandator":"",
      "applicationId":"AFC"
  }

These information are available throughout the submit. The "submitTransactionId" is a UUID generate at the
beginning of the submit. It is used to link all log entries to each other during the submission of the form. The
log statements containing the FormSubmitContext are always having the JSON above attached.
Another important class is the DorPersistenceData class. This class is created per form / subform and
handles an individual formcode and CDOK and stores the generated document. The information there look
as follows:

29.2.2 Technical information
The classes mentioned above overwrite the "toString()" method and return a JSON object out of it. This has
the following advantages:
       In the toString() Method, we can steer what information should be in the log. Example: We don't want
       the CSIV2 token to be part of the log all the time. So we omit it there.
       The JSON can be extracted via Splunk and be formatted. The information gathering is easier.

30.1 FormMetadata Fragment

30.1.1 Background
The afcomplib_all offers the following client lib to obtain the metadata of a form:


  window.forms.ubs.getFormMetadata()

This method extracts the information from the URL in an Online Form. When this function is executed in the
backend (renderDor), the URL is not present. To obtain those information, the "FormMetadata" Fragment
needs to be added to the form as Step 0.


30.1.2 Step by Step


                      Step                                                            Description

 1                   Add a new "Step" to the form and name it
                     "FormMetadata". The Fragment reference is:
                     /content/dam/formsanddocuments/
                     afforms_global_fragmentlib/formmetadata




 2                   Make sure, that it's the Step 0 (this is technically not
                     needed but provides a consistency throughout all
                     forms).
