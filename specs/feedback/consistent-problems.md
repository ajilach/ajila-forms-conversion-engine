# Consistent Problems

Systemic defects that affect **many forms in the same way** — a wrong fragment
used everywhere, an old-engine bug since fixed, a layout convention that changed.
Distinct from [resolved.md](resolved.md), which records one-off, per-feedback-item
resolutions.

Each entry is **data** the `/sweep` engine executes — symptom, how to find
affected forms, how to fix one. The engine is problem-agnostic: it dispatches on
the `Detect` / `Fix` verbs below and has no per-problem logic. A new entry is
**code-free only when it can reuse an existing `Detect`/`Fix` script**; a new
shape (a structural rewrite, an attribute target no regex matches) needs a new,
committed, reviewed `find_`/`set_` script first. See `.claude/skills/sweep/SKILL.md`
→ "Record a new problem".

**Establishing "correct":** a sweep needs a ground-truth reference. The conversion
engine is **not** authoritative by default (it has known faults) — rely on it only
when the user says it's right for this problem; otherwise ask for a reference.

## Entry format

```markdown
## PROBLEM-<slug> — <title>
**Symptom:** what's wrong, and where it shows up in the form .content.xml
**Detect:** grep: <regex>            # how to identify an affected form's deployed XML
            # or → script: <name> <args>   (when a regex can't express it)
**Fix:**    manual: <AI procedure>   # how to fix ONE form
            # or → script: <name> <args>   (deterministic, worth scripting)
**Verify:** must: <regex> ; must-not: <regex>   # optional auto-check (check_form.py) after the fix
**Max changed lines:** <N>                       # optional blast-radius guard (form_diff.py): flag forms whose fix touched more than N lines. Attribute-level fixes only — for additive/structural fixes set it to the expected per-instance insert size, or omit and rely on Verify / the fix's `ok`.
**Origin:** feedback-recurrence | engine-diff | manual
**Tracking:** #<n>                   # the consistent-problem GitHub issue
**Status:** open | piloted <YYYY-MM-DD> (N/TOTAL) | swept <YYYY-MM-DD>
```

**Verbs**
- `Detect: grep: <regex>` — the default; matched against each form's
  `.content.xml` by `find_affected.py`.
- `Fix: manual: <procedure>` — the default; the sweep agent edits each form's XML
  with judgment (extract → edit → repack), same discipline as the feedback Worker.
- `Fix: script: <name> <args>` — a deterministic fix. The script takes the form's
  ZIP, transforms its `.content.xml` in place, and prints a JSON report including a
  uniform **`ok`** boolean (form is now in the target state) that `run_sweep`'s
  verify consumes. Existing fixers to reuse: `swap_fragment` (fragRef value),
  `remove_attr` (drop an attribute), `set_attr_on` (ensure an attribute on
  selector-matched elements, quote-aware), `set_fragment_panel` (fragRef + panel
  attributes), `set_dor_template` (entity-aware DoR config). A new *shape* (e.g. a
  structural rewrite that synthesises nested nodes) needs a new such script.
- The whole staged run is executed by `run_sweep.py --slug PROBLEM-<x>
  [--pilot|--continue|--only]`, which reads this entry and does detect → fix →
  delta → diff → verify → deploy → issue row → one PR.

**Two traps in how this file is parsed — both fail silently (learned the hard way 2026-07-27, parsers unified 2026-08-26):**
- **Detect and Fix args are both `shlex.split()` — quote like a shell.** `run_sweep.py`, `apply_sweeps.py`
  and `check_regressions.py::detector_argv()` all split the verb inside the backticks with `shlex.split()` and
  there is no shell, so a value that contains a double quote must be wrapped in single quotes:
  `--select 'name="PN_BR"'`. A bare `name="PN_BR"` is stripped to `name=PN_BR` and matches nothing —
  **the rule reports 0 affected and looks green**. (Until 2026-08-26 `check_regressions` used plain `.split()`,
  so the two verbs needed *opposite* quoting and a quoted selector could not be written for both; the margin
  and checkbox entries carry the scars. Cost of the original trap: 258 affected forms reported clean, #55
  unenforced for weeks.) Quote-free tokens (`--select controls/metadata`) split the same either way.
- **The on/off switch is `"swept" in Status` — a substring test on that one line.** So any wording that
  merely *mentions* the word enrols the rule in the guard, the intake app and `apply_sweeps`. Keep it
  out of the `Status:` line until the corpus really is done.

## PROBLEM-step-title-panel — Each wizard step's title wrapped in a step-title panel
**Symptom:** the engine wraps every wizard **step**'s title in a dedicated *step-title panel* (`guidePanel` named `{step}Title`, holding a `headingLevel="2"` title-draw) as the step's **first child** (engine `profiles/ubs/aem/panel.xml`; **engine confirmed authoritative for this problem** by the owner — *but only for the wrap structure; the engine does NOT reliably detect the title text, so title text comes from the deployed form, never the engine*). A *step* = a panel directly under `guideContainer › rootPanel(guideRootPanel) › items`, excluding the specials (`summary`/`preview`/`formmetadata`/`signerInfo`/…). Per-step verdict (the agreed rule — title text taken **verbatim** from the form, this sweep only changes *structure*):
- **ok** (609) — already has a dedicated step-title panel, **or a child draw already renders the title** (a `titledraw`/`textdraw` whose `_value` text *exactly* equals the step title) → **skip** (synthesizing would duplicate the visible heading). **Only a drawn `_value` counts as "rendered" — a panel's `jcr:title` does NOT render as a visible heading** (validated on AAAI `PN_Agreement`, AACB `PN_Parte1`, `PN_StpSectionIiSectionTitle` — all panels whose `jcr:title` matched the step title but showed no heading; those steps need synth, not skip).
- **wrap:move** (77) — a `headingLevel="2"` draw exists but isn't wrapped → **move that draw intact** to the top of the step and wrap it; remove the step's own `jcr:title`. Translation-safe (validated: AAAM move kept its German title).
- **wrap:synth** (274) — no draw renders the title → synthesize a draw from the step's `jcr:title` at the top; remove the step's `jcr:title`. Covers steps whose title only lived in a panel `jcr:title` (AAAI, AACB sections, AAAL — all validated single after).
- **strip:double** (26) — already wrapped (a `headingLevel="2"` draw whose text *equals* the step's own `jcr:title`) **and** the step still carries that `jcr:title` → AEM renders the heading **twice on screen** (`dorExcludeTitle` only hides it in the DoR/PDF, not the form) → **strip the redundant step `jcr:title`** (no insert). Validated: AACB first two showed twice, single after.
- **wrap:promote** (45) — no h2 draw and no step `jcr:title`, **but the step LEADS with a `titledraw`** (its real title rendered at the wrong heading level: `h3`/`h4`/none) → promote that draw to a proper step title: set `headingLevel="2"` + `css="stepTitle"`. **If it's already inside a dedicated step-title panel** (17 of 45) → promote **in place** (no new panel — else double-wrap); **otherwise** (28 of 45) → move it intact to the top and wrap it in `{name}Title`. A leading *textdraw* (body text) or no draw → stays titleless. Validated: AACT (in-place, single panel), AAEU "Checkliste"/AAFA "Finanzdienstleister" (move).
- **flag:trans** (7) — `jcr:title` is translation-linked (path-keyed) and no draw renders it → auto-wrap + flag "update translations".
- **titleless** (31) — no title anywhere (no h2 draw, no `jcr:title`, and the leading drawn element is a textdraw/body or absent) → **skip**.

Rules that made the fix safe (all from AEM validation): **remove the step's own `jcr:title`** when wrapping (else AEM renders it a second time), **a panel `jcr:title` never renders a visible heading** (so only a matching drawn `_value` blocks a synth — everything else gets a proper title), and **strip the step `jcr:title` when a wrapped draw already shows the same text** (`strip:double`). Translations are text-keyed (`dictionary/<lang>.xml`, `sling:key="fd_<text>"`), so keeping title text verbatim preserves them.

Detection keys on a `headingLevel="2"` title-draw, **not** `css="stepTitle"` (that marker also sits on wrapper panels / `textdraw`s and is absent on ~415 — it both over- and under-matches). **182 forms / 422 auto-fixes (77 move + 274 synth + 26 strip + 45 promote) / 7 flags** of 286 packages.
**Detect:** script: `find_step_title_panel.py`  _(emits `wrap[]` {form,step,source:move|synth|strip|promote,title} and `flag[]` {…,reason}; that is the review surface — verify it before building/running the fix)_
**Fix:** script: `set_step_title_panel.py` _(byte-offset structural surgery: insert a `{name}Title` panel as the step's first child; `move` = relocate the existing draw intact (preserves translations), `synth` = build a draw from `jcr:title`, `strip` = remove the redundant step `jcr:title` (no insert), `promote` = a leading titledraw at the wrong heading level → set `headingLevel=2`+`css=stepTitle` (in place if already in a title panel, else move+wrap); all also remove the step's own `jcr:title` and set `dorExcludeTitle="true"` to match the engine. Auto-fixes `move`+`synth`+`strip`+`promote`+`flag:trans`; skips `ok` and `titleless`. Mirrors the detector's skip rules. Prints `{inner, wrapped:[{step,source}], ok}`.)_
**Verify:** the fix script's per-step `ok` (well-formed result + every targeted step now has a first-child step-title panel, or had its redundant title stripped) + a pilot **visual spot-check** (title shows once, correctly). The 2 `flag:trans` steps are auto-wrapped too but **listed in the issue table as "update translations"** — the owner tops up their translations after rollout.
**Max changed lines:** omit — additive structural insert; gate on removed==0 (move adds/relocates, never deletes content) + the fix's per-step `ok`.
**Origin:** manual (engine-confirmed for structure only)
**Tracking:** #18
**Status:** **swept 2026-06-30 (182/182 fixed + deployed, PR #19 merged).** Detector + fixer validated in AEM on AAAM (move, translation held), AAAN (synth), AACB (strip:double + 26 section synths), AAAI/AAAL (synth, no double), AACT/AAEU/AAFA (promote). Three rule corrections during the pilot: added `strip:double` (AACB's first two doubled); tightened `renders_title_elsewhere` to **draw `_value` only** (a panel `jcr:title` doesn't render → titles living only in a panel `jcr:title` are now synthed); added `wrap:promote` (titleless step leading with a titledraw at the wrong heading level → promote to h2, in place if already in a title panel else move+wrap). The 7 `flag:trans` steps (4 forms) were resolved **not-actionable** — all are `jcr:language="en"` with orphaned dictionaries (no live second locale), so the English synth titles are correct. 31 steps remain genuinely titleless. One edge: `contentPanel_forInternalBankUseOnly` (1 form) is a direct root child that looks like content, not a step.

**Dependency:** this is the **prerequisite** the jump-to-field sweep (#12) is deferred behind — jump-to-field's button goes on the step-title draw, which must first be correctly wrapped. **Land #18 before re-piloting #12.** Also overlaps banking (#10) / dor-template (#14) on the same `_merged.zip`s → sequence rollouts (merge one, rebase + `--continue` the rest; the fix re-derives each zip from base, so idempotent).

## PROBLEM-panel-type-ubs — Every panel must be the UBS custom panel
**Symptom:** a panel uses the **default AEM panel** (`sling:resourceType="fd/af/components/panel"`) instead of the **UBS custom panel** (`ajila-forms-customers/ajila-forms-ubs/components/controls/panel`). That covers wizard panels, step-title panels, repeatable **wrappers** (owner directive 2026-07-20), **fragment-reference panels (`fragRef`)** — which the retired [PROBLEM-fragment-panel-aem](#) / #24 used to force the other way — and **container nodes with no `guideNodeClass`**. Corpus at widening: **1,668** occurrences across **304 forms** = 1,666 on `guideNodeClass="guidePanel"` nodes (all of them fragment panels; the non-fragment scope was already clean) + **2 `<items>` container nodes** (BBDY_033, BBDZ_019 — the `items` of a `PN_Definitions_Accordion` panel, where a *layout* normally sits; one hand-authored source copied twice). **Max changed lines:** omit — one attribute value changed per swapped panel (no adds/removes); gate on the fix's `ok` + re-scan.
**Origin:** owner directive 2026-08-24 (blanket UBS panel). Overrides the engine on both sub-cases: `repeatable.xml` emits the repeatable outer wrapper as the default AEM panel, and `fragment.xml` emits fragment panels as the default AEM panel — the owner does not want either in the deployed forms.

## PROBLEM-repeatable-add-label — A repeatable's Add button must name what it adds
**Symptom:** the Add button of a repeatable reads a bare `Add` (or a label in the wrong language, or one naming the wrong entity) instead of naming the entity it appends — `Add client`, `Kunden hinzufügen`, `Aggiungere legale rappresentante`. **Only repeatables that have an Add button are in scope**; one without a button is ignored.
**The subject** is read from the form, first hit wins: the first drawn text inside the repeating panel (or, when it holds a fragment, that fragment's own first title) → the heading **immediately above** the panel → a single word shared by every field label in the panel, one field being enough → and as a last resort the repeatable's own name, then its container's, through a closed hint list. "Immediately above" is looked up through the wrapper panels the repeatable sits in — a heading is often a sibling of an ancestor, not of the panel — but only while the node is the *first* child of its parent, since anything else in between means the heading belongs to that instead; and into a `{…}Title` panel when that is what sits above, since PROBLEM-step-title-panel wraps a title in a panel of its own. A subject over 4 words or 42 characters is prose and goes to manual, and is not treated as a heading at all.
**The label** is `Add <noun>` / `<Substantiv> hinzufügen` / `Aggiungere <sostantivo>` / `Añadir <sustantivo>` with the noun from the concept dictionary in the form's **base language** — the majority language of the form's own inline titles, since the dictionary list names the *translations*, not the base. An English-based form also gets `fd_<label>` entries in each of its de/it/es dictionaries; a form authored in German or Italian keeps its own language and gets none.
**A dictionary word is matched at the start of a word, leftmost first, longest first.** German compounds a word into longer ones (`Kundendaten` is a `kunde`) but `Abgeltungsteuerbefreite` is not an `Erbe`; a heading names its subject before qualifying it, so `Depotinhaber (nachstehend Kunde)` is about the Depotinhaber; and the more specific reading wins, so `Kontoinhaber` is an account holder and not an account, and `Cliente` is the Italian word and not the English `client` inside it. A `/i`, `/e`, `/s` tail is a plural marker, not a word.
**When the base language cannot be decided, the label goes out in English with its translations.** A word two languages share (`Cliente`, `Firma`) counts for whichever of them the form's other titles vote for, and for none of them otherwise; a tie, or nothing but shared words to go on, means English.
**The rule only touches a bare `Add` and the literals it knows are wrong.** A button that already reads something of its own is `kept`: not rewritten, not flagged, not counted — the reviewer is the one who judges wording. Rewriting it would undo a correction as fast as it is made, which would make the rule's own mistakes impossible to escape (the `Kunde`/`Depot` kind of bug would keep coming back), and flagging it would leave a form red for good over wording nobody has to justify to a script. The exception is `KNOWN_WRONG`, an explicit list of literals the converter hands out wrongly — today `Add legale rappresentante` and `Aggiungere rappresentante autorizzato`, the same Italian strings stamped on panels that are not about that entity and in forms that are not in Italian. Those the fix does overwrite. To make the rule act on any other wording, add the literal to that list or teach `CONCEPTS` the word.
**The Add button is found by ownership, then by scope and proximity.** A form reuses the name `BT_Add` for every repeatable, and two repeatables can share a name, so the name identifies nothing on its own. A button whose script adds an instance of *this* repeatable first is its own, wherever it sits and however many there are — a configurator repeats the same panel with one Add button per variant, and they all get the same label. Otherwise: search the repeatable's container and at most three ancestors above it, stop at the first level holding a candidate, take the nearest — but never a button another repeatable of this form owns, since one button often appends a row to a data panel *and* to its signature twin, and it is labelled from the panel it was placed with. A repeatable left with no button of its own stays out of scope. When two repeatables do end up on one button wanting different text, both go to manual: writing either would leave the other wrong and each pass would undo the last.
**Skip (39 forms, 2026-08-04):** not checked by the **corpus** guard — the intake app passes `--no-skip`, so a package arriving again is checked in full — buttons the fix cannot label — nothing on screen names what they add (31), the only text is prose (4), or two repeatables share the button (4). Each needs a person to write the label; drop the form from this line when someone does. ## PROBLEM-visible-on-init — Visibility rules must also run on Initialize
**Symptom:** a visibility rule only fires when a value it depends on **changes**. On a freshly opened form — or one reloaded from a draft — nothing has changed yet, so the rule never runs and the component keeps whatever `visible` state the author left on the node: panels that should be hidden are showing, panels that should be shown are missing, until the user happens to touch the controlling field. Every visibility rule must therefore also run at **Initialize**. **Origin: manual (UBS directive 2026-08-06).**

**A verbatim copy would be a no-op — the *result* has to become an assignment.** A visibility rule communicates through its evaluated result (`… true; } else { … false; }`); an Initialize rule's result is discarded. So the copy rewrites the result into `this.visible = …`. That is the corpus's own convention, not an inference: **441 Initialize scripts already use `this.visible`**, and so do 15 visibility rules. Everything else in the script — notably the `window.forms.ubs.showAFShowDor(this)` / `hideAFHideDor(this)` calls the engine emits — is copied unchanged, so the DoR follows visibility at init exactly as it does on change.

**Four result shapes, all mechanical.** `bare` **527** — bare `true;`/`false;` statements → `this.visible = true/false;`; a literal inside a ternary is deliberately not matched. `expr` **266** — the value is a trailing bare expression (`this.parent.instanceIndex+1 == …;`) → `this.visible = (…);`. `assign` **15** — already assigns `this.visible` → copied verbatim. `sideeffect` — no boolean result at all (only calls, e.g. `hideAFHideDor(…)`) → copied verbatim, which is what the hand-authored forms already ship. Unclassifiable → `manual`, never auto-fixed; **0 today**.

**Both storage lineages carry visibility rules, and never both on one node:** `fd:rules` **316** (visual rule editor; the value's `script` is the machine-generated code *string*) and `fd:scripts` **501** (code editor; `script` is an *object* with `content`). The copy is always written as a SCRIPTMODEL appended to `fd:scripts` / `fd:init` — the only shape that can express `this.visible = …` (the visual editor cannot) and the shape AEM itself writes. A multi-value `fd:init` holding several independent SCRIPTMODELs is corpus-attested (AAAA_019), so the **80 components that already initialize something else are never rewritten**: the copy becomes an additional value and runs after theirs. 3 components have no `fd:scripts` node at all and get one, placed after their `fd:rules` sibling.

**Why this needed new code.** An AF rule is not an attribute a regex can patch: it is a JCR **multi-value String** property whose values are JSON documents, FileVault-escaped inside an XML attribute (values separated by *unescaped* commas, commas *inside* a value escaped `\,`, a leading `{`/`[` escaped on single-valued properties). Getting that codec wrong silently corrupts every rule on the form, so `decode`/`encode` are byte-exact inverses — verified by round-tripping **all 7767** `fd:rules`/`fd:scripts` values in the corpus (`python3 .claude/scripts/visible_init.py --selftest`, which also unit-tests the four rewrites). The new SCRIPTMODEL's `field` is derived from the XML ancestry rather than copied from the source rule: the stored `field` is **stale on more than half the corpus's rules** (rules get copy-pasted between forms and survive renames). It is editor metadata — the runtime binds `this` to the node the rule hangs on — so a derived value is strictly better.

**Extent: 155 of 286 packages, 808 rules on 805 components.** 9 further rules are already on Initialize (hand-fixed long ago on AAAL_019/AACJ_019) and are skipped — the same check that makes the sweep idempotent. Simulated end to end: **155/155 `ok`**, 808 rules added, re-scan reports **0 affected**, every form well-formed, **no attribute other than `fd:init` changed anywhere**, all display attributes (`jcr:title`/`_value`/`options`/`fd:translationIds`/`bindRef`/`css`/`visible`/`dorExclusion`) byte-identical, and all 80 pre-existing Initialize values preserved verbatim as a prefix.
**Detect:** script: `find_visible_init.py`  _(per component: a visibility rule whose rewritten body is not already an Initialize rule on that same component. `--report` emits the per-instance review surface — component · category · before → after. Affected = exactly what the Fix repairs, so the guard clears itself. Idempotent.)_
**Fix:** script: `set_visible_init.py`  _(quote-aware open-tag scan — rule JSON and rich text contain literal `>` — with byte-offset splices applied back-to-front, so nothing else is re-serialised. Prints `{inner, components, rules_added, by_category, existing_init_appended, scripts_nodes_created, remaining, ok}`; `ok` = the detector's own logic finds nothing left on the result.)_
**Verify:** the fix's `ok` + a re-scan showing 0 affected + a pilot **visual check in AEM: open a form whose first step has conditional panels and confirm the right panels are visible IMMEDIATELY, before touching any field** — that first-load state is the entire point of the sweep and no script can see it. Also confirm nothing that should be hidden is showing.
**Max changed lines:** 160   _(≈1 line per component; 73 is the corpus worst case — AAHQ_019 with 71 rules. Flag anything beyond ~2× that.)_
**Origin:** manual (UBS directive 2026-08-06 — visibility rules never run on a freshly loaded form)

The fixer therefore compares the *message*, not just the key, and rewrites a stub in place; the detector flags one as `dict-stub`. Anything that is neither the English master nor a wording this sweep itself superseded is treated as a human translation and never touched.

**Translation provenance — adopt the corpus wording, don't invent a rival.** Where the corpus already carried an authored translation, that exact phrasing is used, so the same sentence doesn't ship in two wordings: `de` both messages, `sp` both messages (the "Por favor, …" form), `it` both (from the BBPT_019 / AAPC_033 node attributes). Only `fr` had no precedent and is authored here. An earlier pass of this sweep shipped its own `de` phone and `sp` wordings before that survey was done; those strings are listed in `email_phone_labels.SUPERSEDED` so the fixer overwrites them. After the sweep the corpus has exactly **one** wording per language per message — re-check with the per-language tally in the closing comment on #117 before adding any new locale.

**Source types — a whitelist, and why (found in self-review, and by the owner spotting a miss).** The label heuristic converts only from `controls/textbox` and `controls/numericbox`. **numericbox matters**: AAPC_033's two contact fields ("Numero telefonico aziendale", "Numero di fax") are numeric boxes carrying `displayPictureClause="num{(zz,zzz,…zz)}"`, which reformats a phone number as `1,234,567.00` and rejects a leading `+` — strictly worse than the textbox case, and invisible to a textbox-only detector. Surveying *every* `/controls/` type for a phone/email label turns up 25 further matches and **all 25 are false positives**: 20 `panel` (the field's own CONTAINER — `PN_Fax_FCGroup1`, `PN_Email` — matched on its name, or a section title), 2 `textdraw`, 1 `tertiarybutton` ("Aggiungere indirizzo e-mail"), 1 `checkbox` (a consent line mentioning Telefax-Banking), and 1 `textboxMultiline` (AAIQ_019's letterhead `AF_Sender_Additional_References` relabelled "Fax" — a multiline→single-line change is a different, riskier edit, deliberately left alone). Hence `CONVERTIBLE_FROM` is a whitelist, not a blacklist.

**Two over-reaches caught in self-review — both would have shipped silently.**
- **`textIsRich` is NOT enforced.** All 63 reference instances carry `[true,true,true]`, but that is a property of their lineage, not of being an email/telephone component: 44 of the 92 candidate textboxes carry the letterhead lineage's 4-element `[true,true,true,true]`. Forcing 3 elements would have rewritten an unrelated attribute on nearly half the nodes. Beware the general trap — an attribute being unanimous across the reference set is not evidence it *belongs* to the component.
- **`CANON_OPTIONAL` applies only when normalising in place.** It exists to preserve the two deliberate `{0,14}` phone clause variants on nodes that are *already* telephones. Honouring it on a *conversion* would have let a numericbox keep its `num{(zz,…)}` display clause. So `canon_gap`/`rewrite_tag` take an `in_place` flag.

**Disabled fields are excluded.** 10 nodes (all `AF_Sender_State`, the letterhead's Canton/State slot relabelled to show the advisor's phone) carry `enabled="{Boolean}false"`. They are read-only and system-populated, so validation and an autofill hint buy nothing, while `^([+]|00)…` could reject a local-format value ("044 234 56 78") and make the form unsubmittable. The check runs **last** in `classify`, after the label matches — running it first floods the near-miss audit list with all 287 disabled textboxes. Note the editable sibling in the same letterhead (`AF_CA_Phone`, `enabled=true`) **is** converted.

**Coverage-gap pass (2026-08-19, #125) — three holes the first rollout left, and why its own detector reported clean.** A re-audit (independent broad-lexicon scan of all 53k control nodes, three label probes instead of one) confirmed **no over-conversion** — all 150 converted nodes carry a genuine contact label, no email↔telephone mix-up, no disabled node converted — but found 23 missed instances in 7 forms. The `Status: swept` line stays as-is through this pass: dropping it would un-enrol the rule from the CI regression guard for the whole corpus, which is worse than a temporarily incomplete corpus (the guard's PR mode only checks *changed* forms, so the pass's own PR stays green, and the full-corpus backstop only sees the new detector once the PR lands with the fixes).
- **A CamelCase name is not a word list (5 nodes, BAUL_033).** `classify`'s name fallback split on `_` only, so `TXT_NumeroDiTelefonoFisso` never matched `\btelefono\b` — no boundary before `Fisso`. These 5 are the **older lineage's label shape**: the label lives in a sibling `titledraw` (`TTL_NumeroDiTelefonoFisso`) and the field carries no `jcr:title` at all, so the name is the only probe there is. The same form's second contact block *was* converted, so its own twins are the reference. Fixed by splitting camel humps too (`email_phone_labels.name_probe`); measured against all 478 untitled input nodes in the corpus it newly classifies **exactly** those 5, zero false positives. The converted nodes stay untitled — the fix never invents a `jcr:title`.
- **An absent dictionary key is invisible to a stub check (16 entries, 5 forms).** The fixer derived the messages to insert from *this run's conversions*, so (a) **AAGB_019** — 3 email + 3 telephone nodes that were **already canonical** — was never "affected" and got no message at all, rendering English in all 6 of its non-English locales; and (b) **AAAA_019 / AAAL_019 / AAKN_019 / AANF_019** each ship a full `es.xml` **and** a sparse second Spanish `sp.xml`; only the kind converted in that run reached `sp`. The detector could not see either, because it only flagged a *present* key with an English message. Now `add_masters` comes from the **post-fix components** and the detector reports an absent key as `dict-missing`.
- **Two regional locales were never written (2 entries, BANS_019).** It ships **only** `fr-ch` and `it-ch` (no plain `fr`/`it`), and neither is in `default_translations.TARGET_LOCALES`, so both files were skipped and French and Italian readers got the English message. Added as `email_phone_labels.EXTRA_LOCALES` (`fr-ch`→fr, `it-ch`→it) rather than by editing `TARGET_LOCALES`, which drives the already-swept **default-translations** rule — widening it there would silently change that sweep's scope. Collapsing regional variants is the same rule **PROBLEM-metadata-languages** applies.
- **Correctly left alone**, re-confirmed in the audit: the deny-list labels, the 11 disabled `AF_Sender_State` letterhead slots, the 2 multiline `Fax` fields, the `immobile`/`automobili`/`valori mobiliari` false friends, and ABEP_033's `Nome di dominio (ad es. @musterdomain.com)` — a domain, not an address. Corpus labels are EN/IT/DE only (no form is French- or Spanish-labelled), and a broad fr/es lexicon (`courriel`, `téléphone`, `portable`, `correo electrónico`, `móvil`) returns zero unconverted hits — the language-shaped damage was in the **locale map**, not the label wording.

**Two things the gap-pass pilot established (2026-08-19) — expect them on every future run.**
- **`delta` flags every telephone conversion, and it is a validator gap, not a regression.** Converting a textbox to `controls/telephone` changes `guideNodeClass` from `guideTextBox` (known to the engine MCP's validator) to `guideTelephone` (not known), so the delta gate reports "new violation — … has unknown guideNodeClass guideTelephone". It is **pre-existing corpus-wide debt**: the same validator reports the identical complaint on *untouched, already-deployed* packages (AAFK_019 → 3, AAAA_019 → 12). And the value is right by the engine's own intent — `profiles/ubs/aem/telephone.xml` emits `guideNodeClass="guideTelephone"` and `config.toml` sets `css_telephone = "widget_ajila-forms-ubs-phonebox"`, i.e. the engine now **agrees with the corpus-derived CANON** on both. (The engine has since gained `email.xml`/`telephone.xml` templates — the "no email/telephone template" in the Symptom above was true when written, and the built binary's validator still lags them, the documented stale-binary trap.) So: accept a `delta` flag whose only content is `unknown guideNodeClass guideTelephone`; investigate any other delta text.
- **`sp.xml` appears not to be served by AEM — a known unknown, see #17.** AAGB_019 carries our email/phone message in **both** `es.xml` and `sp.xml` after the fix, yet the deployed render gives `afAcceptLang=es` → Spanish and `afAcceptLang=sp` → **English**. So the four `sp`-only gaps (AAAA/AAAL/AAKN/AANF_019) are **correct-by-consistency but not demonstrably user-visible**; `es` is the locale AEM actually serves. Do not claim a rendering improvement for an `sp`-only fix without re-testing. The genuinely user-visible wins of this pass are AAGB_019 (de/de-ch/es/fr/it all verified rendering their translation, previously English everywhere) and BANS_019 (`fr-ch` → French, `it-ch` → Italian, verified).

**Review note (human, per form):** the converted fields must still render correctly — check that a phone field shows the phonebox styling and rejects a non-`+`/`00` value, that an email field rejects a malformed address, and that no label or layout shifted. Fax fields are deliberately converted to the *telephone* component (owner decision), so their error text reads "valid phone number" — that is expected, not a defect.

## PROBLEM-metadata-languages — Metadata summary control: language list + master language must match the languages the form was issued in
**Symptom:** the hidden metadata control in the summary panel (`sling:resourceType="ajila-forms-customers/ajila-forms-ubs/components/controls/metadata"`, `visible="false"`, inside `summarypanel`) carries two language fields that disagree with the languages the form was actually issued in: `formrange_afmasterlanguage` on the control, and `formrange_language` (the comma-separated list) on every `<entities>` direct-child item. **65 of 304 packages affected** (61 change the list, 27 the master); 239 already correct. Both attributes already exist on all 304 packages, so the fix only ever rewrites a value — it never inserts an attribute or touches node structure.
**The rule (owner-confirmed 2026-08-20 — supersedes the 2026-08-18 rule, see the revision note):** the list is exactly the languages the form was *issued* in, which is exactly the set of source PDFs delivered for it:
```
languages = { source-PDF languages }          forms/issued/<F>/<F>_<LANG>.pdf
            { the region's language }         when the form has NO source PDF at all
master    = that language if there is exactly one; otherwise the region's language
            (019 -> DE, 033 -> IT, else EN), falling back to EN when the region's
            language is not one of the form's own
```
Regional variants collapse (`de-ch`→DE, `es`→SP, `en-us`/`en-gb`→EN, `it-ch`→IT, `fr-ch`→FR); the `DEFAULT` pseudo-language is dropped (4 forms carry it). List order is EN-first-then-alphabetical, matching the owner's `EN,DE,IT,SP` example — but order is **cosmetic**: nothing parses this value and the corpus already mixes `DE,EN` with `EN,IT`, so the detector compares language **sets** and never flags a form merely to reorder it. **`master ∈ languages` holds for all 304 packages** under this rule, which the previous one could not manage.
**The dictionaries are deliberately NOT a signal — that was the defect.** Until 2026-08-20 the rule unioned in "locales with a genuine translation", where *genuine* meant a dictionary key no earlier sweep injected. A key is not a translation: the conversion writes a key set for every locale the source carries, and `sling:message` is then left empty or echoing the key. **AAIA_019** is the reference case — `fr.xml` and `it.xml` hold **81 keys each with 0 actual translations**, which is how FR and IT got into the list of a form issued only in DE/EN/SP (`de` 57, `de-ch` 45, `es` 56 real entries; `en`/`sp` hold nothing but #72 residue). The dictionaries also cannot ever name the form's own language — nothing is translated into the language it is written in — so they can only narrow a list, never complete one. `metadata_languages.translated_langs()` survives as an **audit aid only**: the detector reports it on flagged forms, so a form carrying real translations its issued-language list does not name stays visible. **34 of the 65 affected forms are in that state** (AAAI_019 is issued DE+EN but really is translated into IT and SP; AAHD_019 is issued DE/EN/SP and translated into all five). Deciding whether such a form should be *re-issued* with more PDFs or have the translations dropped is an owner call per form, not something this sweep infers.
**The source PDFs sit NEXT TO the package.** `forms/issued/<F>/<F>_<LANG>.pdf` is the only detector input in this repo that is not inside the ZIP, so **any one-form harness must carry those filenames** (bytes are irrelevant — only the `_<LANG>.pdf` suffix is parsed). `scripts/intake/core.py` does this in `_place_source_pdfs`, called from both `_check_harness` and `_bulk_harness`. Without it the intake app reports "remove EN" on a form that is green in the repo, `apply_sweeps` (which runs in the real worktree, where the PDFs exist) writes the language straight back, and the check can **never** go green — the exact loop reported for AAIA_019 on 2026-08-20. Parity test: on a 30-form sample the harness matched the repo verdict 30/30 with the stand-ins and 19/30 without.
**Reference:** the owner's directive above plus the **complete source-PDF delivery** of 2026-08-20 (`OneDrive_1_20.8.2026.zip`, 690 files, `<Country>/<Tranch>/<FORM>_<LANG>.pdf`) — a strict superset of what the repo held (0 repo-only files), which is what makes "exactly the PDFs" a usable rule. 100 files were added, creating 61 form directories; 584 of the 587 pre-existing files were byte-identical. **AAIA_019 → `EN,DE,SP`, master `DE`.**

## PROBLEM-visual-editor-rules — Rules must be code-editor JavaScript, not visual-editor rules
**Symptom:** components carry rules authored in the **visual rule editor**: the component's `<fd:rules>` node holds a rule property whose value is a rule-tree JSON (`nodeName:"ROOT"`) with the machine-generated JavaScript in its `script` key. Every rule must instead be a **code-editor** rule — a SCRIPTMODEL value on the component's `<fd:scripts>` node (the shape AEM itself writes for the code editor; 10'000+ corpus-attested values) — with the `fd:rules` node left canonically **empty** (`<fd:rules jcr:primaryType="nt:unstructured"/>`, the corpus norm: 8'627 of them, and PROBLEM-toolbar-nav-handler's blessed target shape). **838 rules in 224 of 304 packages** (fd:visible 324, fd:click 234, fd:valueCommit 142, fd:init 112, fd:calc 23, fd:validate 3); 61 are disabled (`enabled:false`). **Origin: manual (owner directive 2026-08-24).**

**The conversion is mechanical, and behaviour-preserving by construction.** A visual rule stores BOTH the clickable rule tree (editor metadata only) and the machine-generated JavaScript that actually executes; all 838 parse and carry that script (0 bad JSON, 0 missing bodies), and every value's `eventName` matches its property. The move is: same code (the `/** machine-generated */` banner is stripped — it warns about the visual editor, which no longer applies), same event, same property name, `enabled` preserved (`enabled:false` is corpus-attested on fd:scripts — 739 values — so a disabled rule stays disabled instead of being silently activated), and the SCRIPTMODEL's `field` derived from the XML ancestry, not copied (the stored one is stale on copy-pasted rules — same lesson as visible-on-init). After the sweep the rule is viewed and edited in the code editor only; what is lost is exactly the visual-editor representation, which is the point.

**Two shapes on one component is real, and ordering there is the pilot's check.** 379 components carry the same event property in **both** lineages; the converted value is **appended after** the existing code-editor values, and the pre-conversion relative execution order between the lineages is not observable from the package. The corpus's one verbatim duplicate (AACQ_019 `BT_Remove` — a **disabled** visual click rule whose script already sits enabled on fd:scripts) is dropped, not doubled; an **enabled** rule always converts verbatim, twin or no twin (dropping one against a disabled twin would deactivate a running rule).
