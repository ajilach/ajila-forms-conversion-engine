# Consistent Problems

Systemic defects that affect **many forms in the same way** — a wrong fragment
used everywhere, an old-engine bug since fixed, a layout convention that changed.
Distinct from [resolved.md](resolved.md), which records one-off, per-feedback-item
resolutions.

Each entry is **data** the `/sweep` engine executes — symptom, how to find
affected forms, how to fix one. The engine is problem-agnostic: it dispatches on
the `Detect` / `Fix` verbs below and has no per-problem logic. A new entry is
**code-free only when it can reuse an existing `Detect`/`Fix` script**; a new
shape (a structural rewrite, an attribute target no regex matches) needs a new,
committed, reviewed `find_`/`set_` script first. See `.claude/skills/sweep/SKILL.md`
→ "Record a new problem".

**Establishing "correct":** a sweep needs a ground-truth reference. The conversion
engine is **not** authoritative by default (it has known faults) — rely on it only
when the user says it's right for this problem; otherwise ask for a reference.

## Entry format

```markdown
## PROBLEM-<slug> — <title>
**Symptom:** what's wrong, and where it shows up in the form .content.xml
**Detect:** grep: <regex>            # how to identify an affected form's deployed XML
            # or → script: <name> <args>   (when a regex can't express it)
**Fix:**    manual: <AI procedure>   # how to fix ONE form
            # or → script: <name> <args>   (deterministic, worth scripting)
**Verify:** must: <regex> ; must-not: <regex>   # optional auto-check (check_form.py) after the fix
**Max changed lines:** <N>                       # optional blast-radius guard (form_diff.py): flag forms whose fix touched more than N lines. Attribute-level fixes only — for additive/structural fixes set it to the expected per-instance insert size, or omit and rely on Verify / the fix's `ok`.
**Origin:** feedback-recurrence | engine-diff | manual
**Tracking:** #<n>                   # the consistent-problem GitHub issue
**Status:** open | piloted <YYYY-MM-DD> (N/TOTAL) | swept <YYYY-MM-DD>
```

**Verbs**
- `Detect: grep: <regex>` — the default; matched against each form's
  `.content.xml` by `find_affected.py`.
- `Fix: manual: <procedure>` — the default; the sweep agent edits each form's XML
  with judgment (extract → edit → repack), same discipline as the feedback Worker.
- `Fix: script: <name> <args>` — a deterministic fix. The script takes the form's
  ZIP, transforms its `.content.xml` in place, and prints a JSON report including a
  uniform **`ok`** boolean (form is now in the target state) that `run_sweep`'s
  verify consumes. Existing fixers to reuse: `swap_fragment` (fragRef value),
  `remove_attr` (drop an attribute), `set_attr_on` (ensure an attribute on
  selector-matched elements, quote-aware), `set_fragment_panel` (fragRef + panel
  attributes), `set_dor_template` (entity-aware DoR config). A new *shape* (e.g. a
  structural rewrite that synthesises nested nodes) needs a new such script.
- The whole staged run is executed by `run_sweep.py --slug PROBLEM-<x>
  [--pilot|--continue|--only]`, which reads this entry and does detect → fix →
  delta → diff → verify → deploy → issue row → one PR.

**Two traps in how this file is parsed — both fail silently (learned the hard way 2026-07-27):**
- **`Detect:` args must NOT be quoted, `Fix:` args MUST be.** `check_regressions.py::detector_argv()`
  splits the Detect verb with plain `.split()` and there is no shell, so `--select 'a="b"'` reaches the
  script *with* the quotes and matches nothing → **the rule reports 0 affected and looks green**.
  `apply_sweeps.py` / `run_sweep.py` split the Fix verb with `shlex.split()`, which strips quotes, so
  there they are required. (Cost: 258 affected forms reported clean, and #55 was unenforced for weeks.)
- **The on/off switch is `"swept" in Status` — a substring test on that one line.** So any wording that
  merely *mentions* the word enrols the rule in the guard, the intake app and `apply_sweeps`. Keep it
  out of the `Status:` line until the corpus really is done.

## PROBLEM-step-title-panel — Each wizard step's title wrapped in a step-title panel
**Symptom:** the engine wraps every wizard **step**'s title in a dedicated *step-title panel* (`guidePanel` named `{step}Title`, holding a `headingLevel="2"` title-draw) as the step's **first child** (engine `profiles/ubs/aem/panel.xml`; **engine confirmed authoritative for this problem** by the owner — *but only for the wrap structure; the engine does NOT reliably detect the title text, so title text comes from the deployed form, never the engine*). A *step* = a panel directly under `guideContainer › rootPanel(guideRootPanel) › items`, excluding the specials (`summary`/`preview`/`formmetadata`/`signerInfo`/…). Per-step verdict (the agreed rule — title text taken **verbatim** from the form, this sweep only changes *structure*):
- **ok** (609) — already has a dedicated step-title panel, **or a child draw already renders the title** (a `titledraw`/`textdraw` whose `_value` text *exactly* equals the step title) → **skip** (synthesizing would duplicate the visible heading). **Only a drawn `_value` counts as "rendered" — a panel's `jcr:title` does NOT render as a visible heading** (validated on AAAI `PN_Agreement`, AACB `PN_Parte1`, `PN_StpSectionIiSectionTitle` — all panels whose `jcr:title` matched the step title but showed no heading; those steps need synth, not skip).
- **wrap:move** (77) — a `headingLevel="2"` draw exists but isn't wrapped → **move that draw intact** to the top of the step and wrap it; remove the step's own `jcr:title`. Translation-safe (validated: AAAM move kept its German title).
- **wrap:synth** (274) — no draw renders the title → synthesize a draw from the step's `jcr:title` at the top; remove the step's `jcr:title`. Covers steps whose title only lived in a panel `jcr:title` (AAAI, AACB sections, AAAL — all validated single after).
- **strip:double** (26) — already wrapped (a `headingLevel="2"` draw whose text *equals* the step's own `jcr:title`) **and** the step still carries that `jcr:title` → AEM renders the heading **twice on screen** (`dorExcludeTitle` only hides it in the DoR/PDF, not the form) → **strip the redundant step `jcr:title`** (no insert). Validated: AACB first two showed twice, single after.
- **wrap:promote** (45) — no h2 draw and no step `jcr:title`, **but the step LEADS with a `titledraw`** (its real title rendered at the wrong heading level: `h3`/`h4`/none) → promote that draw to a proper step title: set `headingLevel="2"` + `css="stepTitle"`. **If it's already inside a dedicated step-title panel** (17 of 45) → promote **in place** (no new panel — else double-wrap); **otherwise** (28 of 45) → move it intact to the top and wrap it in `{name}Title`. A leading *textdraw* (body text) or no draw → stays titleless. Validated: AACT (in-place, single panel), AAEU "Checkliste"/AAFA "Finanzdienstleister" (move).
- **flag:trans** (7) — `jcr:title` is translation-linked (path-keyed) and no draw renders it → auto-wrap + flag "update translations".
- **titleless** (31) — no title anywhere (no h2 draw, no `jcr:title`, and the leading drawn element is a textdraw/body or absent) → **skip**.

Rules that made the fix safe (all from AEM validation): **remove the step's own `jcr:title`** when wrapping (else AEM renders it a second time), **a panel `jcr:title` never renders a visible heading** (so only a matching drawn `_value` blocks a synth — everything else gets a proper title), and **strip the step `jcr:title` when a wrapped draw already shows the same text** (`strip:double`). Translations are text-keyed (`dictionary/<lang>.xml`, `sling:key="fd_<text>"`), so keeping title text verbatim preserves them.

Detection keys on a `headingLevel="2"` title-draw, **not** `css="stepTitle"` (that marker also sits on wrapper panels / `textdraw`s and is absent on ~415 — it both over- and under-matches). **182 forms / 422 auto-fixes (77 move + 274 synth + 26 strip + 45 promote) / 7 flags** of 286 packages.
**Detect:** script: `find_step_title_panel.py`  _(emits `wrap[]` {form,step,source:move|synth|strip|promote,title} and `flag[]` {…,reason}; that is the review surface — verify it before building/running the fix)_
**Fix:** script: `set_step_title_panel.py` _(byte-offset structural surgery: insert a `{name}Title` panel as the step's first child; `move` = relocate the existing draw intact (preserves translations), `synth` = build a draw from `jcr:title`, `strip` = remove the redundant step `jcr:title` (no insert), `promote` = a leading titledraw at the wrong heading level → set `headingLevel=2`+`css=stepTitle` (in place if already in a title panel, else move+wrap); all also remove the step's own `jcr:title` and set `dorExcludeTitle="true"` to match the engine. Auto-fixes `move`+`synth`+`strip`+`promote`+`flag:trans`; skips `ok` and `titleless`. Mirrors the detector's skip rules. Prints `{inner, wrapped:[{step,source}], ok}`.)_
**Verify:** the fix script's per-step `ok` (well-formed result + every targeted step now has a first-child step-title panel, or had its redundant title stripped) + a pilot **visual spot-check** (title shows once, correctly). The 2 `flag:trans` steps are auto-wrapped too but **listed in the issue table as "update translations"** — the owner tops up their translations after rollout.
**Max changed lines:** omit — additive structural insert; gate on removed==0 (move adds/relocates, never deletes content) + the fix's per-step `ok`.
**Origin:** manual (engine-confirmed for structure only)
**Tracking:** #18
**Status:** **swept 2026-06-30 (182/182 fixed + deployed, PR #19 merged).** Detector + fixer validated in AEM on AAAM (move, translation held), AAAN (synth), AACB (strip:double + 26 section synths), AAAI/AAAL (synth, no double), AACT/AAEU/AAFA (promote). Three rule corrections during the pilot: added `strip:double` (AACB's first two doubled); tightened `renders_title_elsewhere` to **draw `_value` only** (a panel `jcr:title` doesn't render → titles living only in a panel `jcr:title` are now synthed); added `wrap:promote` (titleless step leading with a titledraw at the wrong heading level → promote to h2, in place if already in a title panel else move+wrap). The 7 `flag:trans` steps (4 forms) were resolved **not-actionable** — all are `jcr:language="en"` with orphaned dictionaries (no live second locale), so the English synth titles are correct. 31 steps remain genuinely titleless. One edge: `contentPanel_forInternalBankUseOnly` (1 form) is a direct root child that looks like content, not a step.

**Dependency:** this is the **prerequisite** the jump-to-field sweep (#12) is deferred behind — jump-to-field's button goes on the step-title draw, which must first be correctly wrapped. **Land #18 before re-piloting #12.** Also overlaps banking (#10) / dor-template (#14) on the same `_merged.zip`s → sequence rollouts (merge one, rebase + `--continue` the rest; the fix re-derives each zip from base, so idempotent).

## PROBLEM-visible-on-init — Visibility rules must also run on Initialize
**Symptom:** a visibility rule only fires when a value it depends on **changes**. On a freshly opened form — or one reloaded from a draft — nothing has changed yet, so the rule never runs and the component keeps whatever `visible` state the author left on the node: panels that should be hidden are showing, panels that should be shown are missing, until the user happens to touch the controlling field. Every visibility rule must therefore also run at **Initialize**. **Origin: manual (UBS directive 2026-08-06).**

**A verbatim copy would be a no-op — the *result* has to become an assignment.** A visibility rule communicates through its evaluated result (`… true; } else { … false; }`); an Initialize rule's result is discarded. So the copy rewrites the result into `this.visible = …`. That is the corpus's own convention, not an inference: **441 Initialize scripts already use `this.visible`**, and so do 15 visibility rules. Everything else in the script — notably the `window.forms.ubs.showAFShowDor(this)` / `hideAFHideDor(this)` calls the engine emits — is copied unchanged, so the DoR follows visibility at init exactly as it does on change.

**Four result shapes, all mechanical.** `bare` **527** — bare `true;`/`false;` statements → `this.visible = true/false;`; a literal inside a ternary is deliberately not matched. `expr` **266** — the value is a trailing bare expression (`this.parent.instanceIndex+1 == …;`) → `this.visible = (…);`. `assign` **15** — already assigns `this.visible` → copied verbatim. `sideeffect` — no boolean result at all (only calls, e.g. `hideAFHideDor(…)`) → copied verbatim, which is what the hand-authored forms already ship. Unclassifiable → `manual`, never auto-fixed; **0 today**.

**Both storage lineages carry visibility rules, and never both on one node:** `fd:rules` **316** (visual rule editor; the value's `script` is the machine-generated code *string*) and `fd:scripts` **501** (code editor; `script` is an *object* with `content`). The copy is always written as a SCRIPTMODEL appended to `fd:scripts` / `fd:init` — the only shape that can express `this.visible = …` (the visual editor cannot) and the shape AEM itself writes. A multi-value `fd:init` holding several independent SCRIPTMODELs is corpus-attested (AAAA_019), so the **80 components that already initialize something else are never rewritten**: the copy becomes an additional value and runs after theirs. 3 components have no `fd:scripts` node at all and get one, placed after their `fd:rules` sibling.

**Why this needed new code.** An AF rule is not an attribute a regex can patch: it is a JCR **multi-value String** property whose values are JSON documents, FileVault-escaped inside an XML attribute (values separated by *unescaped* commas, commas *inside* a value escaped `\,`, a leading `{`/`[` escaped on single-valued properties). Getting that codec wrong silently corrupts every rule on the form, so `decode`/`encode` are byte-exact inverses — verified by round-tripping **all 7767** `fd:rules`/`fd:scripts` values in the corpus (`python3 .claude/scripts/visible_init.py --selftest`, which also unit-tests the four rewrites). The new SCRIPTMODEL's `field` is derived from the XML ancestry rather than copied from the source rule: the stored `field` is **stale on more than half the corpus's rules** (rules get copy-pasted between forms and survive renames). It is editor metadata — the runtime binds `this` to the node the rule hangs on — so a derived value is strictly better.

**Extent: 155 of 286 packages, 808 rules on 805 components.** 9 further rules are already on Initialize (hand-fixed long ago on AAAL_019/AACJ_019) and are skipped — the same check that makes the sweep idempotent. Simulated end to end: **155/155 `ok`**, 808 rules added, re-scan reports **0 affected**, every form well-formed, **no attribute other than `fd:init` changed anywhere**, all display attributes (`jcr:title`/`_value`/`options`/`fd:translationIds`/`bindRef`/`css`/`visible`/`dorExclusion`) byte-identical, and all 80 pre-existing Initialize values preserved verbatim as a prefix.
**Detect:** script: `find_visible_init.py`  _(per component: a visibility rule whose rewritten body is not already an Initialize rule on that same component. `--report` emits the per-instance review surface — component · category · before → after. Affected = exactly what the Fix repairs, so the guard clears itself. Idempotent.)_
**Fix:** script: `set_visible_init.py`  _(quote-aware open-tag scan — rule JSON and rich text contain literal `>` — with byte-offset splices applied back-to-front, so nothing else is re-serialised. Prints `{inner, components, rules_added, by_category, existing_init_appended, scripts_nodes_created, remaining, ok}`; `ok` = the detector's own logic finds nothing left on the result.)_
**Verify:** the fix's `ok` + a re-scan showing 0 affected + a pilot **visual check in AEM: open a form whose first step has conditional panels and confirm the right panels are visible IMMEDIATELY, before touching any field** — that first-load state is the entire point of the sweep and no script can see it. Also confirm nothing that should be hidden is showing.

**Detect:** script: `find_banking_default_de.py`  _(affected = Germany form with ≥1 canonical banking panel missing the Initialize rule; non-Germany forms and non-canonical banking panels are never counted)_
**Fix:** script: `set_banking_default_de.py`  _(appends one Initialize SCRIPTMODEL to each matching panel's `fd:scripts`/`fd:init`, creating the node if absent; an existing Initialize rule on the panel, if any, is never rewritten — additive only, same discipline as `set_visible_init.py`. Non-Germany forms report `ok:true`, untouched.)_
**Verify:** must: `TXT_BankingRelationship1\.value = '0319'` ; must-not: none  _(per-panel correctness — which panel carries which rule on a multi-banking-panel form — is asserted by the fix's own `ok`/`remaining` re-scan, not by a file-level grep)_
**Max changed lines:** 3   _(one new fd:init attribute set/insert per panel; a form with N banking panels legitimately changes more — e.g. AANB_019's 3 panels, same multi-panel exception #10 already flagged and verified benign)_

## PROBLEM-email-phone-component — Email/telephone fields are plain textboxes
**Symptom:** the conversion engine has **no email/telephone template** (`profiles/ubs/aem/` ships only `textbox.xml`), so every field labelled "Email" / "Telephone" / "Mobile phone" / "Fax" is emitted as a plain `controls/textbox`: no format validation, no `autofillFieldKeyword` (`email`/`tel`) for browser autofill, no phonebox styling. 126 instances across 40 of 296 packages (87 node conversions + 39 untranslated dictionary messages). Ground truth is the **corpus, not the engine** — 63 already-correct instances (32 email, 31 telephone) across 26 forms, plus the engine's own fragment library (`affrg_Authorized_Person1`, `affrg_personal-details`); their attribute sets are vendored as `email_phone_labels.CANON`. Where the hand-built fragments disagree with the deployed corpus the corpus wins: telephone `css` is `widget_ajila-forms-ubs-phonebox` (31/31), email drops `css` entirely (31/32).
**Detect:** script: `find_email_phone_component.py --json`  _(a form is affected if a `controls/textbox` has an email/phone/fax label, if an existing `controls/email`/`controls/telephone` deviates from CANON, or if a dictionary carries one of the two message keys with an untranslated English message — the last two buckets are what make the rule idempotent)_
**Fix:** script: `set_email_phone_component.py`
**Verify:** must-not: `sling:resourceType="ajila-forms-customers/ajila-forms-ubs/components/controls/(email|telephone)"[^>]*css="widget_ajila-forms-ubs-textbox"`  _(the real gate is the fix's own `ok`: detector clean for the form AND no email/telephone node left on a non-`EML_`/`TEL_` prefix)_
**Origin:** manual
**Tracking:** #117
**Status:** swept 2026-08-17 (41/41 fixed + deployed; 0 flagged). Scope grew twice during the sweep: +3 forms when untranslated dictionary stubs were found, then +1 (BAUL_033) from a form merged into master mid-rollout — the detector re-scans the corpus each run, so re-running picks those up automatically.

**Label discrimination (the hard part — anchoring, not keyword matching).** `e-mail` requires the `e` prefix, which keeps "Mailing address confirmation" out; `\bmobil` keeps "immobili"/"automobili" out (a letter precedes `mobil`); `telefon\b` keeps "Telefonische Bestellung" out (the boundary fails before `ische`). The remaining 10 near-misses are an explicit, hand-checked `DENY_LABEL`/`DENY_NAME` list in `email_phone_labels.py` — run `find_email_phone_component.py --report` to see both the conversions and the denied residue side by side. Two denials are judgment, not typos: "Telefonico canale n." is a channel identifier, and ABEP_033's "Titolare / Numero di telefono in caso di domande" packs a holder NAME and a number into one field, so the numeric-only clause would reject valid input. The 386 untitled textboxes are all letterhead/address fields and none classify.

**Ordering dependency — the fixer chains the rename itself.** Changing the resourceType changes the required name prefix (`find_naming_violations.TYPE_PREFIX`: email→`EML`, telephone→`TEL`), so leaving a converted node on `TXT_` would turn the already-swept **PROBLEM-naming-conventions** guard red. `set_email_phone_component.py` therefore re-runs `set_naming_prefix.py` after the type change (which also rewrites references). `AF_`-prefixed letterhead/binding names are exempt in the naming rule and keep their names — that is deliberate, renaming them would break the sender-block bindings. Note the fix's `ok` is scoped to **this** sweep and deliberately does NOT inherit `set_naming_prefix.ok`, which reports False on a pristine BANR_033 too (the owner-accepted duplicate `TTL_Authorized_User`).

**Message localisation (owner decision 2026-08-14) — CONFIRMED WORKING.** 31 of the 32 deployed instances hardcode the English `validatePictureClauseMessage` even in German/Italian forms. This sweep instead puts the message in each form's per-locale dictionary as an `fd_<master>` entry, reusing the `default-translations` mechanism (`default_translations.render_entry`, byte-identical formatting). **Verified empirically on the pilot**, not assumed: fetching the DAM preview with `?wcmmode=disabled&afAcceptLang=<loc>` renders the translated message for every locale the form ships a dictionary for, and English for the rest (AACT_019 `de→de fr→fr it→it`, AAAA_019 `es→sp`, AAGZ_033/BANR_033 `it→it`). So the per-node `fd:translationIds` fallback (BBBO_019 / BBPT_019) is **not** needed. A form with no dictionary at all (AAPC_033, BAQM_033) keeps the English message — both declare `jcr:language="en"`, so that is correct, and the fix never creates a dictionary file a form doesn't already have.

**Untranslated stubs — a present key is NOT a translation (#72 again).** 39 entries across 15 forms already carried `fd_<master>` with the **English text** as `sling:message`, so AEM rendered English in that locale. An "insert if the key is missing" fix silently leaves those broken — AAGZ_033 rendered English in Italian on the first pilot pass despite having both keys. The fixer therefore compares the *message*, not just the key, and rewrites a stub in place; the detector flags one as `dict-stub`. Anything that is neither the English master nor a wording this sweep itself superseded is treated as a human translation and never touched.

**Translation provenance — adopt the corpus wording, don't invent a rival.** Where the corpus already carried an authored translation, that exact phrasing is used, so the same sentence doesn't ship in two wordings: `de` both messages, `sp` both messages (the "Por favor, …" form), `it` both (from the BBPT_019 / AAPC_033 node attributes). Only `fr` had no precedent and is authored here. An earlier pass of this sweep shipped its own `de` phone and `sp` wordings before that survey was done; those strings are listed in `email_phone_labels.SUPERSEDED` so the fixer overwrites them. After the sweep the corpus has exactly **one** wording per language per message — re-check with the per-language tally in the closing comment on #117 before adding any new locale.

**Source types — a whitelist, and why (found in self-review, and by the owner spotting a miss).** The label heuristic converts only from `controls/textbox` and `controls/numericbox`. **numericbox matters**: AAPC_033's two contact fields ("Numero telefonico aziendale", "Numero di fax") are numeric boxes carrying `displayPictureClause="num{(zz,zzz,…zz)}"`, which reformats a phone number as `1,234,567.00` and rejects a leading `+` — strictly worse than the textbox case, and invisible to a textbox-only detector. Surveying *every* `/controls/` type for a phone/email label turns up 25 further matches and **all 25 are false positives**: 20 `panel` (the field's own CONTAINER — `PN_Fax_FCGroup1`, `PN_Email` — matched on its name, or a section title), 2 `textdraw`, 1 `tertiarybutton` ("Aggiungere indirizzo e-mail"), 1 `checkbox` (a consent line mentioning Telefax-Banking), and 1 `textboxMultiline` (AAIQ_019's letterhead `AF_Sender_Additional_References` relabelled "Fax" — a multiline→single-line change is a different, riskier edit, deliberately left alone). Hence `CONVERTIBLE_FROM` is a whitelist, not a blacklist.

**Two over-reaches caught in self-review — both would have shipped silently.**
- **`textIsRich` is NOT enforced.** All 63 reference instances carry `[true,true,true]`, but that is a property of their lineage, not of being an email/telephone component: 44 of the 92 candidate textboxes carry the letterhead lineage's 4-element `[true,true,true,true]`. Forcing 3 elements would have rewritten an unrelated attribute on nearly half the nodes. Beware the general trap — an attribute being unanimous across the reference set is not evidence it *belongs* to the component.
- **`CANON_OPTIONAL` applies only when normalising in place.** It exists to preserve the two deliberate `{0,14}` phone clause variants on nodes that are *already* telephones. Honouring it on a *conversion* would have let a numericbox keep its `num{(zz,…)}` display clause. So `canon_gap`/`rewrite_tag` take an `in_place` flag.

**Disabled fields are excluded.** 10 nodes (all `AF_Sender_State`, the letterhead's Canton/State slot relabelled to show the advisor's phone) carry `enabled="{Boolean}false"`. They are read-only and system-populated, so validation and an autofill hint buy nothing, while `^([+]|00)…` could reject a local-format value ("044 234 56 78") and make the form unsubmittable. The check runs **last** in `classify`, after the label matches — running it first floods the near-miss audit list with all 287 disabled textboxes. Note the editable sibling in the same letterhead (`AF_CA_Phone`, `enabled=true`) **is** converted.

**Review note (human, per form):** the converted fields must still render correctly — check that a phone field shows the phonebox styling and rejects a non-`+`/`00` value, that an email field rejects a malformed address, and that no label or layout shifted. Fax fields are deliberately converted to the *telephone* component (owner decision), so their error text reads "valid phone number" — that is expected, not a defect.
